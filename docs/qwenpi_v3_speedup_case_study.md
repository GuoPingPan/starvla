## 第 0 章：故事是怎么开始的

我们训练这个模型时，8 张 A800 跑出来 **每步 2.83 秒，吞吐 37.65 samples/s**。

单看这个数字没感觉。但一个反常的对照是：**同事的 PI05 模型（3.3B 参数，比我们大 3 倍）
在同样 8 卡上，每样本耗时和我们差不多**。

> 💡 **小白视角**：模型大 3 倍却跑得一样快，就好比一辆 3 吨的卡车和一辆 1 吨的轿车
> 跑出了相同的时速——轿车一定哪里出了问题。**这种"和参照系比不对劲"的感觉，
> 是性能优化最可靠的起点**。不要问"为什么这么慢"，先问"和同类比正常吗"。

## 第 1 章：预备知识充电桩（已熟悉的同学可跳过）

### 1.1 训练的"一步"到底在发生什么

深度学习训练的主循环长这样：

```
取一批数据 (batch)
   ↓
前向 forward：数据过模型，算出预测，得到 loss（一个标量，代表"错多少"）
   ↓
反向 backward：从 loss 出发反推每个参数的梯度（"往哪调能错得少一点"）
   ↓
优化器 optimizer：用梯度更新参数
   ↓
循环……
```

每一步的耗时 ≈ `取数据 + 前向 + 反向 + 优化`。性能优化的全部内容就是：
**搞清楚这四段时间各花在哪，然后把大头砍掉。**

### 1.2 GPU 是怎么"算"的：kernel、SM、显存

- **kernel（内核）**：GPU 的一次"任务单"。你在 PyTorch 里写 `torch.mm(a, b)`，
  背后就是发射（launch）一个 kernel 到 GPU 上执行。一步训练 = 发射成千上万个 kernel。
- **SM（流式多处理器）**：GPU 里的"工位"。A800 有 108 个 SM，可以理解为 108 个工人。
  `SM 利用率 80%` = 平均有 86 个工人在干活；`21%` = 只有 23 个人在干活，其他在摸鱼。
- **显存**：GPU 的内存。放三样东西：模型参数、优化器状态、以及**激活**（前向算出来的
  中间结果，反向时要用，所以必须存着——这通常是最大头）。

> 💡 **关键认知**：GPU 慢有两种完全不同的原因——
> ① 工人都满负荷但活太多（**计算受限**）；② 活不多但派单流程太慢，工人在等
> （**等待受限**，行话叫 launch-bound / host-bound）。**两者的药方完全不同**，
> 吃错药不但没用还可能更慢。怎么区分是第 4 章的重头戏。

### 1.3 精度：fp32 / bf16 / Tensor Core

- **fp32**：每个数用 32 位存储，1 位符号 + 8 位指数 + 23 位尾数（有效数字约 7 位）。
- **bf16**：指数位和 fp32 一样宽（8 位，所以**数值范围不缩小、不会溢出**），
  尾数只有 7 位（有效数字约 2-3 位）。
- **A800 上的物理差异**：fp32 矩阵乘法走普通算术单元（~19.5 TFLOPS）；
  bf16 走 **Tensor Core**（专用矩阵乘电路，~312 TFLOPS）。**理论差 16 倍，实际通常兑现 2-4 倍。**

> 💡 **小白视角**：bf16 = 用 2 位有效数字记账 vs fp32 的 7 位。听起来很亏？
> 但训练本身就是个噪声很大的过程（每批数据的梯度本身抖动 10-100%），2-3 位有效数字
> 的舍入误差淹没在噪声里。这也是全行业（GPT、LLaMA……）默认 bf16 训练的原因。

### 1.4 混合精度（autocast）：自动挡的省心与坑

`torch.autocast("cuda", dtype=torch.bfloat16)` 的语义：**在这个代码块里，PyTorch 自动
把支持的计算降到 bf16，同时把"怕精度损失"的操作自动保护在 fp32**。

受保护的算子白名单（背下来，面试有用）：

| 自动保持 fp32 的算子 | 为什么 |
|---|---|
| `layer_norm` / `group_norm` | "求方差再开方"对舍入敏感 |
| `softmax` / `log_softmax` | 指数运算放大误差 |
| `mse_loss` / 各类 loss | loss 是最终汇总数，不能糊 |
| `pow` / `exp` / `log` | 同上 |

所以"混合精度"= **大计算量的矩阵乘法降 bf16 提速，小而敏感的计算留在 fp32 保命**。

坑：autocast 是**嵌套覆盖**的——外层开了 bf16，内层再写一个
`autocast(dtype=torch.float32)`，内层就整个回到 fp32。本文第 3 章的 bug 1 就是这个。

### 1.5 多卡训练与 ZeRO

8 张卡怎么分工？最朴素是 DDP（每张卡放完整模型，各算各的批次，最后对齐梯度）。
模型大了显存放不下，就有了 **ZeRO** 分级策略：

| 方案 | 每卡重复存的东西 | 每步通信量 |
|---|---|---|
| DDP | 参数+梯度+优化器全量 | 2×P |
| ZeRO-1 | 参数+梯度（优化器分片） | 3×P |
| ZeRO-2 | 参数（梯度+优化器分片） | **2×P** |
| ZeRO-3 | 无（全分片） | 更复杂 |

（P = 参数量对应的字节数。）注意 ZeRO-2 通信量已经是最优档，**换 ZeRO-1 不会更快**
（第 5 章会讲我们差点犯这个错）。

### 1.6 观测工具：性能剖析（profile）

我们用的是仓库自带的 `PerformanceAnalyzer`（`STARVLA_PROFILE=1` 开启），它会在训练中
挑一个窗口（比如第 21-28 步）记录：

- 每个 kernel 的名字、执行时长、时间戳（导出成 Chrome trace 文件）
- SM 利用率 / 功率 / 显存的后台采样
- 前向/反向/优化器的分段计时

**最重要的思维转换**：profile 报告不是"打分卡"，而是"体检报告 + 解剖图"。
光看摘要框里的"诊断结论：COMPUTE / MIXED"是不够的，真正的宝藏是把 trace 文件
（一个大 JSON）自己拿来分析——本文所有关键发现都来自对 trace 的二次挖掘。

## 第 2 章：第一轮优化 —— 消灭 FP32（84% 的 GPU 时间在跑"慢挡"）

### 2.1 证据：kernel 名字会说话

对第一次 profile 的 trace 做 kernel 分类统计，结果吓人：

| kernel 类别 | 占 GPU 时间 | 说明 |
|---|---|---|
| `ampere_sgemm_*`（6 种） | **83.7%** | **FP32** 矩阵乘 |
| bf16 GEMM | 3% | 本该是主角 |
| elementwise/norm 小操作 | 少量 | |
| `fmha_cutlassF_f32` | 少量 | 连注意力都是 fp32 版 |

> 💡 **小白视角**：kernel 的名字是"供词"。`sgemm` 的 s = single precision = fp32；
> `bf16gemm` / `s16816gemm` 才是走 Tensor Core 的 bf16 矩阵乘。
> 名字里带 `f32` 的注意力 kernel 同理。**不用读一行模型代码，精度问题在 kernel
> 层面已经裸奔了。**

### 2.2 顺藤摸瓜：从 kernel 到代码

trace 里的每个 kernel 都能通过 ID 关联到发起它的 PyTorch 算子（`aten::mm` /
`aten::addmm`，即矩阵乘）。这些算子来自哪个模块？用 `grep` 搜框架代码里的精度关键词：

```bash
grep -n "autocast\|float()\|torch_dtype" starVLA/model/framework/VLM4A/QwenPI_v3.py
```

一下就搜到了两处问题（见下）。**这套"kernel → 算子 → 代码"的回溯链是所有 GPU
性能定位的标准姿势。**

### 2.3 Bug 1：`autocast(float32)` 把动作头整个按回慢挡

```python
# QwenPI_v3.forward 里的原始代码:
with torch.autocast("cuda", dtype=torch.float32):   # ← 内层覆盖了外层的 bf16!
    actions_target_repeated = actions_target.repeat(...)
    action_loss = self.action_model(...)             # 356M 参数的 DiT 全在 fp32 跑
```

而对照组 PI05 的同一段代码**没有**这层包裹——它跟着训练器外层的
`autocast(bf16)` 走（train_starvla.py:674）。这是移植代码时带入的偏差。

**修复**：改成 `torch.autocast("cuda", dtype=torch.bfloat16)`。
（推理路径 `predict_action` 保留 fp32——推理只跑一次 batch=1，精度比速度值钱。）

### 2.4 Bug 2：配置错位，静默 fallback 到 16

flow-matching 训练每条动作要采一组 (时间步 t, 噪声) 来算损失。代码里有个
`repeated_diffusion_steps` 控制采几组：

```yaml
# yaml 里写的(意图: 2 组):
framework:
  action_model:
    repeated_diffusion_steps: 2
```

```python
# 代码里读的(位置对不上!):
repeated_diffusion_steps = self.config.trainer.get("repeated_diffusion_steps", 16)
#                                                   ^^^^^^ 读的是 trainer 段     ^ fallback=16
```

**yaml 写在 `framework.action_model` 下，代码却从 `config.trainer` 读 → 读不到 →
静默用了 fallback 值 16。** DiT 的等效 batch = 16 × 16 = 256 序列，全 fp32。

> 💡 **小白视角（本案例最痛的一课）**：**yaml 写了 ≠ 生效了**。这种错不报错、不警告，
> 一切看起来正常。防身技能：
> ① 代码里读配置时打一行 log，启动时肉眼确认；
> ② 修改配置后看相关指标是否真的变了；
> ③ fallback 值尽量保守（默认 4 不会死人，默认 16 就是事故）。

**修复**：读取优先级改为 `trainer 覆盖 > framework.action_model > 默认 4`，让 yaml
里的 `2` 真正生效；随后为对齐 PI05 口径进一步设为 `1`。

### 2.5 为什么 repeat=16 是纯浪费（一个漂亮的等价性）

repeat=16 的本质：**同样的数据/噪声预算，用 8 倍计算换 1/8 的优化器更新次数**
（每条动作采 16 组噪声求平均，梯度方差小一点，但每步贵 16 倍）。

而我们的数据集只有 30 条 episode、14 万帧。20k 步 × 128 条/步 × 16 组噪声，
冗余到离谱。设成 1 之后：**同样的墙钟时间换 16 倍的优化器步数**，对小数据集
只有好处。参考系：PI05 每条动作每步只采 1 组（`OpenPI_ActionHead.prepare_flow_targets`）。

### 2.6 修复效果 + 精度验证

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 每步耗时 | 2.83s | **0.75s** |
| FP32 sgemm | 17.3s / 8步 | **0ms** |
| 显存峰值 | 60.3GB | 19.6GB |
| loss 曲线 | 1.49→0.30 | 同轨迹收敛，无 NaN |

> 💡 **规矩**：**任何"提速"改动都必须附带精度对照**。我们用 12-step 冒烟看 loss
> 是否正常、用每 20 步的在线 `eval/mse` 和修复前对比（0.0115 vs 0.0121，噪声级差异）。
> 速度优化把模型训废了是经典事故。

## 第 3 章：第二轮优化 —— GPU 只忙 20%，80% 时间在等 Python

第一轮修完，以为结束了？profile 一看：**SM 利用率只有 21%，功率 119W（满载 400W），
GPU 大部分时间在摸鱼**。新问题：它在等什么？

### 3.1 先算总账：GPU busy vs idle

把 trace 里所有 kernel 的时间线取并集（GPU 真正在执行的时间），除以窗口墙钟：

```
每步 wall ≈ 1.37s
GPU 真在算 ≈ 0.27s (20%)
GPU 在等   ≈ 1.10s (80%)   ← 新的大象
```

### 3.2 把"等"拆成直方图（关键一步）

"idle 80%"是个糊的结论。把所有相邻 kernel 之间的空隙（gap）按长度分桶：

| gap 长度 | 总量/步 | 每种长度对应什么 |
|---|---|---|
| 0.1–1ms × 海量 | ~590ms | **python 算子间衔接**：一步发 ~1 万个 kernel，每个之间几十微秒的调度开销 |
| <0.1ms × 更海量 | ~250ms | kernel 发射（launch）本身的死区 |
| 步间 140-230ms 一大段 | ~180ms | 取数据→CPU 上的文本 tokenize→拷到 GPU |

> 💡 **小白视角**：三种"等"的三种药——
> 算子间衔接和 launch 死区 → 药方是"融合/少发任务单"（compile / CUDA Graphs）；
> 步间大段 → 药方是"预处理搬到别的线程"；
> 如果是通信在等 → 药方完全不同（见 5.2）。
> **不拆开就吃药 = 蒙。

### 3.3 两点法解出固定开销（一个漂亮的 trick）

我们做过 batch size 扫描（bs 16/32/64/96/128 各跑 24 步测吞吐）。假设每步时间 =
`每样本计算 c × batch + 固定开销 F`，用两个点联立：

```
bs16:  1.37 = 16c + F
bs128: 7.15 = 128c + F
→  c = 51.6ms/样本,  F ≈ 0.54s/步
```

**bs16 时 39% 的步时间是和 batch 无关的固定宿主开销！** 这解释了为什么大 batch
吞吐更高（固定开销被摊薄），也预告了 3.2 里那些 gap 的总账。

### 3.4 host 剖析抓到"cast 风暴"

给 profiler 开 `with_stack`（记录 python 调用栈），看 **CPU 侧**的算子统计：

```
aten::copy_      4153 次/步
aten::to         3283 次/步
aten::_to_copy   2066 次/步      ← 合计 ~9500 次 dtype 转换/步！
```

原因：autocast 下，**fp32 存储的权重每次参与矩阵乘都要现场转一份 bf16**
（backbone 是 bf16 加载的所以没事，随机初始化的 DiT 是 fp32，中招）。

**修复**：DiT 权重直接以 bf16 常驻内存（`self.action_model.to(torch.bfloat16)`）。
DeepSpeed 的 bf16 模式会自动为优化器维护 fp32 主权重，**更新数学仍然是 fp32**。

精度验证：eval/mse bf16 权重 0.0253 vs fp32 权重 0.0262 / 0.0280 —— 噪声内，通过。

### 3.5 第二轮结果（诚实汇报）

| 指标 | 变化 |
|---|---|
| 显存 | 19.6 → **15.9GB**（省 3.7GB，符合预期） |
| 每步耗时 | **基本持平 ~0.75s** |

为什么 8 卡下 cast 消除没转化成提速？因为那 0.54s 固定开销的**主体是 eager Python
执行本身**（HF 模型 24 层 + DiT 逐算子的调度），cast 只是其中一部分。单卡冒烟里
model 段实测 -8%，8 卡被其他 host 工作淹没了。**性能优化常常这样：修对了一件事，
但它不在关键路径上，收益兑现不了——这也是必须实测的原因。**

## 第 4 章：三次失败的尝试（负结果也是资产）

### 4.1 torch.compile：model 快了 17%，整体反而慢了 3 倍

torch.compile 能把几十个小 kernel 融合成几个（正对 3.2 节的病症），看起来是灵药。

实测（DiT 开 compile，单卡 30 步）：model 段 0.41→0.34s（**-17%**），但每步整体墙钟
从 0.44s 恶化到 ~1.4s。原因：dynamo（compile 的调度器）**每次调用都要做守卫检查
（guard）判断输入形状有没有变**，我们序列长度逐 batch 变，调度开销吃掉全部收益还倒贴。

处置：代码保留钩子（`STARVLA_COMPILE` 环境变量，默认关），commit message 里写清楚
负结果和数据，留给后人。

### 4.2 DS bucket 调小：通信不降反升

分析发现 NCCL 通信与计算**零重叠**（kernel 并集 = 各自加和，即从不同时发生），
梯度同步在步尾串行爆发。猜想：DeepSpeed 的 `reduce_bucket_size=5e8`（500MB 拼一车
才发货）太大，改成 5e7 让它小批多跑、插进 backward 的空档。

实测：comm 从 143ms/步**涨到** 158ms/步——小桶 = 更多次集合通信 = 更多固定开销，
而"零重叠"是结构性的（我们的 backward 又短又碎，天然藏不住通信）。回滚。

### 4.3 换 ZeRO-1：被理论账当场否决

直觉："模型才 1.2B，ZeRO-2 是给大模型的吧，换 ZeRO-1 更轻？"

查表（1.5 节）：ZeRO-1 通信量 3×P **大于** ZeRO-2 的 2×P。ZeRO-1 只是拿"梯度不
分区"换显存——而我们显存根本不缺。方向就是错的，一行代码没写。

> 💡 **三连败的共同教训**：这三次尝试全部来自"看起来应该行"；而全部成功的修复
> （fp32 定位、repeat16、cast 风暴）**无一例外来自 profile 证据**。
> 动手之前先拿数据，动手之后必须实测，错了立刻回滚并留档。

## 第 5 章：大 batch 的经济学（最便宜的提速往往在配置里）

显存从 60GB 降到 16GB 后，同样的卡能塞 4 倍的 batch。扫一遍：

| batch | 吞吐 samples/s | 显存 | 每步耗时 |
|---|---|---|---|
| 16 | 93.5 | 21.4GB | 1.37s |
| 32 | 113.1 | 29.2GB | 2.26s |
| 64 | 120.1 | 43.1GB | 4.26s |
| 96 | 131.5 | 57.8GB | 5.84s |
| 128 | **143.1** | 71.6GB | 7.15s |

**但注意一个反直觉的坑**——取决于你的目标：

- 目标是"**跑完固定 20k 步**"（比如和 PI05 基线对照）：batch 越大墙钟**越慢**
  （7.6h → 39.7h），因为每步的活变多了，固定开销摊薄救不回来；
- 目标是"**消化固定量的数据**"（N 个 epoch）：batch 越大墙钟**越快**
  （同样 2.56M 样本：b16 要 7.6h，b128 只要 5.0h）。

两个前置检查别忘了：
① **LR 要随 global batch 缩放**（大致线性：global 128→512 就 ×4）；
② **每步覆盖别超过数据集的可承受比例**（我们 global 1024 vs 14 万帧 = 0.7%/步，安全）。

## 第 6 章：方法论总结（拿走就能用的流程图）

```
① 找参照系: 和同类模型/历史 run 比, 确认"确实不正常" (不是猜)
② 分类体检: kernel 分类统计(GEMM/小操作/通信/注意力) + GPU busy%
     ├─ GEMM 占大头且是 sgemm/f32 → 精度问题, 查 autocast/dtype/配置
     ├─ GPU busy 低 → 等待受限, 拆 gap 直方图:
     │     ├─ 海量小 gap → eager 调度开销 → compile/CUDA graphs/大batch摊薄
     │     ├─ 步间大 gap → 预处理在主进程 → 搬到 worker/缓存
     │     └─ 通信串行 → 查 overlap/bucket/通信量解析式
     └─ 通信占比高 → 算 ZeRO 各档通信量再动手
③ 配置审计: yaml 写了 ≠ 生效了, 确认代码读取路径; fallback 值是否合理
④ 两点法: 扫两个 batch size 联立方程, 量化"每样本成本"和"固定开销"
⑤ 每改一处: 冒烟跑通 → 精度对照(loss/eval 曲线) → 提速量化 → 失败就回滚留档
```

六条心法：

1. **先测量后动手**——所有成功修复来自证据，所有失败来自直觉。
2. **kernel 名字会说话**——sgemm/bf16gemm/f32 这些词直接暴露精度问题。
3. **拆开再吃药**——"idle 80%"没有药方，"590ms 小 gap + 180ms 步间 gap"有。
4. **每改必测**——速度优化不能以 loss 变形为代价。
5. **负结果写进 commit**——避免自己和后人重复踩坑。
6. **最便宜的提速往往在配置里**——这次最大的两个收益（bf16、repeat）一个是删一行
   覆盖、一个是修一个 key 位置，没写一行新算法。

## 术语表

| 术语 | 一句话解释 |
|---|---|
| kernel | GPU 的一次任务单；一步训练发射上万个 |
| SM 利用率 | GPU 工位的平均忙碌比例 |
| fp32 / bf16 | 32 位全精度 / 16 位脑浮点（范围同 fp32、精度低、走 Tensor Core 快 16 倍） |
| Tensor Core | GPU 里专做矩阵乘的电路，bf16 才能用 |
| autocast | PyTorch 混合精度开关：矩阵乘降 bf16，norm/loss 自动保 fp32 |
| 激活 | 前向的中间结果，反向要用必须存，通常是显存大头 |
| ZeRO-1/2/3 | 多卡显存分片策略，等级越高分的越多、通信越复杂 |
| gap 直方图 | 相邻 kernel 之间空隙按时长分桶，区分三种"等" |
| repeat/噪声采样数 | flow-matching 每条动作采几组 (t,噪声)；采多了 = 纯浪费算力 |
| DDP | 最朴素的多卡数据并行，每卡全量模型 |
| launch overhead | 每发射一个 kernel 的固定行政开销（几微秒 × 一万个 = 毫秒级） |
